# AI Prompt 与问题解决记录

> 对应任务 T048。题面允许并鼓励用 AI 辅助开发，但要求 **核心 Agent Runtime 自行实现**。
> 本文件记录：怎么用 AI、用了哪些 prompt、AI 哪里帮上忙、哪里帮倒忙、
> 以及开发过程中真实踩到的坑与解决方式。
>
> 原则：**用 AI 帮助思考，而不是让 AI 代替完成任务**。所有核心逻辑（循环、解析、
> 压缩、隔离）的决策与取舍由人做出，AI 主要用于查漏、review 与边界补齐。

---

## 1. 人机分工

| 环节 | 谁做 | AI 的角色 |
| --- | --- | --- |
| 需求解构与 spec / task 编写 | 人 | 帮我把口语化题面转成可核验的条目，提示我漏掉的验收维度（异常/边界） |
| 技术选型（Python + 零依赖） | 人 | 提供"评审复现成本"这一判断依据 |
| 核心数据结构与分层设计 | 人 | review 分层是否有循环依赖、职责是否越界 |
| 主循环、解析、压缩、隔离实现 | 人 | 按模块生成**候选实现**，我逐行 review 后改写；AI 想当然处由测试兜住 |
| 测试用例设计 | 人定方向，AI 铺量 | 让 AI 列"这个模块可能怎么坏"，我再筛出真正有价值的断言 |
| 边界情况挖掘 | AI 主导 | 这是 AI 最超值的地方（见第 3 节） |
| 文档与记录 | AI 起草，人核对 | 要求它只写代码里真实存在的东西 |

一条贯穿始终的做法：**先写测试，让失败来告诉我实现错在哪**。
本文第 4 节的问题几乎都是被测试抓出来的，而不是靠 code review 看出来的。

## 2. 关键 Prompt 记录

以下 prompt 都是实际使用过的（中文，便于与本文档对照）。

### 2.1 需求结构化

```
读 1.txt，把它整理成 spec.md。要求包含四块核心内容：
1 需求目标（要解决什么问题、最终实现什么功能）
2 功能需求（具体功能 + 主要业务流程）
3 约束条件（必须遵守的规则、兼容性要求、明确不能修改或影响的部分）
4 验收标准（如何判断已正确实现，必须覆盖正常/异常/边界三类）
不要写实现代码。
```

**效果**：第一版 spec 缺了"约束条件"整章，验收标准也只有笼统 11 条。
追问"检查一下有没有包含以上核心内容"后，AI 自己列出了差距并补上
（4.1–4.4 约束、6.1–6.4 共 33 条验收）。

**收获**：让 AI **先自检再补**，比一次性要求"写全"质量高得多。

### 2.2 任务拆分

```
按实施顺序拆分 task.md，从基础准备到功能实现再到测试验收。
每个任务前打 [ ] 标记；每个任务要具体、独立、能明确判断是否完成。
优先复用现有代码和项目架构，不做无关重构。不要增加 spec.md 中没有要求的功能。
```

**效果**：第一版按模块 A–H 并列分组，不符合"实施顺序"；且自作主张加了第 4 个
工具 `weather` 和"UI/CLI 增强"。追问后改为 8 个线性阶段，并明确删掉超纲内容。

**收获**：**"不要增加 spec 未要求的功能"这句必须显式写出来**，
否则 AI 倾向于"顺手多做一个"。

### 2.3 边界情况挖掘（最超值的一类 prompt）

```
针对 agent/context.py 的压缩逻辑，列出所有可能导致它出错的输入情况，
按"会导致崩溃 / 会静默出错 / 会浪费 token"三档分类，不要写代码。
```

**效果**：AI 列出了"单轮本身超长""摘要比原文还长""压缩后 tool_calls 与 tool 失配"
三类。前两类我都没想到，后来都变成了真实修复（见 4.3、4.4）。

### 2.4 代码 review

```
review agent/loop.py 的 run_turn：找出其中"同一份信息被处理两次"或
"状态可能不一致"的地方。只列问题与行号，不要直接改代码。
```

**效果**：AI 指出的问题里有一条是真的（工具结果重复注入，见 4.1）。
让它"只列问题不改代码"很重要——否则它会把代码改乱而我失去对实现的理解。

### 2.5 测试补全

```
tests/test_parser.py 已覆盖：原生 tool_calls、协议 JSON、纯文本回退。
请列出还没覆盖但值得覆盖的解析失败场景，按风险从高到低排序。
```

**效果**：补出"数组包一层 `[{"answer":...}]`""前一个花括号片段非法但后面有合法 JSON"
等场景，后者暴露了真实 bug（见 4.5）。

### 2.6 文档核对

```
根据仓库里真实的代码，写 README 的"系统设计"一节。
所有函数名、文件名、配置项名称都必须与代码一致，不确定的标注"待确认"。
```

**效果**：AI 生成的文档初稿里有 2 处编造的配置项名称，核对时发现并修正。
**教训**：文档类 prompt 必须加"不确定的标注待确认"。

## 3. AI 帮上忙的地方

| 场景 | 具体价值 |
| --- | --- |
| 边界挖掘 | 列出我自己想不到的输入（超长单轮、空摘要、数组包裹 JSON） |
| 测试铺量 | 把"每个工具的异常用例"从 3 条铺到 27 条，且断言具体 |
| 一致性问题 | 指出 `bool` 是 `int` 子类的校验陷阱、`tool_calls` 必须成对回放 |
| 文档草稿 | 把实现细节转成结构化文档，节省大量措辞时间 |
| 概念校对 | 解释 OpenAI 兼容接口对 `role=tool` 配对的硬性要求 |

## 4. AI 帮倒忙 / 我修正的地方

AI 的产出**不能直接采信**。以下是实际被测试或人工 review 抓出的问题，
完整清单见 README 与 task.md 的"完成情况"，这里按"AI 引入 vs 自己写错"归类。

### 4.1 工具结果被注入两次（AI 建议的写法有缺陷）

AI 建议"把工具结果存进 session，同时在循环里把结果拼进 messages 发给 LLM"，
听起来两全其美，实际导致 LLM **每轮收到两份相同结果**（浪费 token，且可能干扰判断）。

**修正**：只保留一个来源——写入 session 的 `role=tool` 消息，下一轮由
ContextBuilder 统一渲染。

### 4.2 `sessions or SessionStore()` 静默丢配置（最隐蔽的一个）

`SessionStore` 实现了 `__len__`，**空的 store 是 falsy**，于是
`sessions or SessionStore()` 会把调用方传入的落盘 store 悄悄换成新的内存 store，
`--store` 参数完全失效，且不报任何错。

**修正**：改成 `sessions if sessions is not None else SessionStore()`。
同一个错误也出现在我自己写的测试 helper 里（等号两边的代码都犯了）。

**教训**：AI 生成的 `x or default` 惯用法在有 `__len__`/`__bool__` 的对象上是陷阱。

### 4.3 摘要比要求的还长（数学算错）

压缩摘要设了 `max_summary_chars=600`，实测输出 604 字符。原因是逐字符预算时
漏算了"片段自带省略号 `...`"和"行间换行符"。

**修正**：放弃脆弱的逐字符预算，改为"先构造、后统一裁剪"，
并加 4 条回归测试锁定该不变量（600/300/120/30/10 全部合规）。

### 4.4 压缩后仍可能超限

只保留最近 `keep_recent_turns` 轮时，若某一轮本身就极长，压缩等于没做。

**修正**：加第二阶段丢弃——仍超限则继续丢到只剩最后一轮。

### 4.5 只尝试第一个花括号片段

从散文里提取协议 JSON 时，AI 的实现只取**第一个**括号平衡片段；
当前面存在非 JSON 的 `{...}`（例如中文说明里的 `{'不是 JSON'}`）就直接放弃，
后面真正的协议 JSON 被忽略。

**修正**：改为返回**所有**平衡片段并依次尝试。

### 4.6 解析失败信息被丢弃

`_extract_protocol_json` 在提取失败时 `return None`，把"看起来像 JSON 但解析失败"
这条关键诊断线索一起丢了，导致 trace 里看不出模型到底输出了什么。

**修正**：诊断信息始终追加到调用方传入的 `warnings`，而不是靠返回值带回。

### 4.7 测试读到了真实环境变量（我自己写的测试有 bug）

`test_cli_reports_config_error_without_traceback` 直接读环境变量判断"缺配置"。
平时跑没问题，但**一旦机器上设置了 `LLM_API_KEY`，这个测试会真的发起网络调用**
并断言失败。第一次跑"有密钥 + 全量套件"时才暴露。

**修正**：用 `mock.patch.dict(os.environ, ..., clear=True)` 显式清空相关变量。
**教训**：涉及环境变量的测试必须自己控制环境，不能依赖"当前机器恰好没设"。

### 4.8 其他被测试抓到的细节

| 问题 | 修正 |
| --- | --- |
| `bool` 被 `{"type":"integer"}` 校验通过 | 校验器显式排除 `bool` |
| `__init_subclass__` 在类定义时抛异常，导致 `assertRaises` 包不住 | 修正测试写法 |
| mock 检索把"仅摘要命中"也当相关 | 改为只有标题/关键词命中才算相关 |
| `[{"answer":"x"}]` 数组包一层被误标为协议对象 | 引入 `looks_like_json` 区分两种来源 |
| E2E 断言 `7006652`，实际输出 `7,006,652` | 比较前去掉千分位 |

## 5. 关于"用 AI 帮倒忙"的经验

1. **AI 的默认倾向是"多做"**：多写一个工具、多加一个开关、多引入一个依赖。
   必须用显式约束（"不要增加 spec 未要求的功能"）把它按住。
2. **AI 写的 `or` 默认值、边界预算、括号匹配最容易错**，因为它们在正常输入下都对。
   这正是测试该覆盖的地方。
3. **让 AI 只列问题、不改代码**，是保持自己对实现掌控感的关键做法。
4. **测试是人和 AI 的共同裁判**：本文 8 个真实缺陷里有 7 个是被测试抓出来的，
   而不是 review 看出来的。所以"先写测试"比"让 AI 多 review 几遍"更有效。
5. **AI 生成的文档必须与代码逐项核对**，它会把不存在的配置项写得很像真的。
